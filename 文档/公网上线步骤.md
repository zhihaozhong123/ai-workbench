### 9. 域名配置与 DNS 解析

在域名服务商控制台添加一条 **A 记录**，将域名指向公网服务器 IP：

| 记录类型 | 主机记录 | 记录值       | TTL   |
|----------|----------|--------------|-------|
| A        | @（或子域名如 `app`）| 服务器公网 IP | 600   |

添加后验证解析是否生效：

```bash
nslookup app.example.com
# 或
dig app.example.com
```

> 解析可能需要几分钟到几小时生效，生效后才能继续下面步骤（Let's Encrypt 需要域名能正确解析到服务器才能签发证书）。

### 10. 申请 SSL 证书（Let's Encrypt）

服务器上安装 certbot（以 Ubuntu/Debian 为例）：

```bash
sudo apt update
sudo apt install certbot -y
```

使用 **standalone 模式**（先确保 80 端口未被占用，先 `docker compose stop nginx`）：

```bash
# 停止 nginx 释放 80 端口
docker compose stop nginx

# 申请证书（替换为你的域名）
sudo certbot certonly --standalone -d app.example.com

# 申请成功后证书路径：
#   /etc/letsencrypt/live/app.example.com/fullchain.pem
#   /etc/letsencrypt/live/app.example.com/privkey.pem
```

**自动续期**（Let's Encrypt 证书 90 天有效，需定期续期）：

```bash
# certbot 自带 systemd timer，安装时已自动启用，检查状态：
sudo systemctl status certbot.timer

# 如果没有自动启用，手动添加 cron：
sudo crontab -e
# 添加：0 3 * * * certbot renew --quiet --pre-hook "cd /path/to/xiaoshutong && docker compose stop nginx" --post-hook "cd /path/to/xiaoshutong && docker compose start nginx"
```

### 11. 配置 nginx HTTPS

修改 `nginx.conf`，在 `server { listen 80; }` 前方增加 443 SSL server block，并将原 80 改为 HTTP → HTTPS 重定向：

```nginx
# ---- HTTPS（Tauri updater 生产环境强制要求）----
server {
    listen 443 ssl http2;
    server_name app.example.com;   # 替换为你的域名

    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-RSA-AES128-GCM-SHA256:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-AES128-GCM-SHA256;
    ssl_prefer_server_ciphers off;

    client_max_body_size 50m;

    # ---- 更新清单 JSON ----
    location ~ ^/update/ {
        alias /var/www/updates/;
        default_type application/json;
        add_header Cache-Control "no-cache, no-store, must-revalidate";
    }

    # ---- DMG 下载 ----
    location /download/ {
        alias /var/www/updates/downloads/;
        add_header Cache-Control "public, max-age=86400";
    }

    # ---- 后端 API + WebSocket ----
    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}

# ---- HTTP → HTTPS 重定向 ----
server {
    listen 80;
    server_name app.example.com;   # 替换为你的域名
    return 301 https://$host$request_uri;
}
```

> 注意：需要把上面出现的 `app.example.com` 替换为你的实际域名。原有的 `location /` 代理配置保留在 443 server block 内即可，80 只做重定向。

### 16. 生成强随机 JWT 密钥

`config.py` 内置了生产环境安全检查：当 `ENV=production` 且 `JWT_SECRET` 仍为默认值 `dev-secret-change-me` 时，**后端会直接拒绝启动**。因此上线前必须替换：

```bash
# 生成强随机 JWT 密钥（32 字节 hex = 64 字符）
openssl rand -hex 32
# 输出示例：a1b2c3d4e5f6...（64 位十六进制字符串）
```

将生成的密钥填入 `.env`：

```bash
# .env
JWT_SECRET=a1b2c3d4e5f6...  # 替换为实际生成的 64 位 hex
```

> 这个密钥用于签发和验证用户登录 JWT token，泄露后任何人都能伪造登录态。**绝对不要**用弱密钥或可猜测的字符串。

同时确认 `.env` 中以下 JWT 相关配置合理：

```bash
JWT_ALGORITHM=HS256                        # 签名算法
ACCESS_TOKEN_EXPIRE_MINUTES=30             # 短期 access token 过期时间
REFRESH_TOKEN_EXPIRE_HOURS=720             # 长期 refresh token 过期时间（30 天）
```

### 17. 配置 CORS 跨域来源

`api/app.py` 中 CORS 中间件的逻辑为：

- **生产模式**（`ENV=production`）：`LOCAL_ORIGINS` 仅包含 `tauri://localhost`（桌面端窗口）
- `EXTRA_CORS_ORIGINS` 从 `.env` 的 `EXTRA_CORS_ORIGINS` 读入（逗号分隔），与 `LOCAL_ORIGINS` 合并为最终允许列表

公网上线后，Tauri app 通过 HTTPS 域名请求后端，**需要将 HTTPS 域名加入额外 CORS 来源**，否则浏览器/WebView 的跨域校验会拦截请求：

```bash
# .env
EXTRA_CORS_ORIGINS=https://app.example.com
```

> 如果有多个域名（如 www 和裸域名），用逗号分隔：
> ```bash
> EXTRA_CORS_ORIGINS=https://app.example.com,https://example.com
> ```

> 注意：nginx 反代已经通过 `X-Forwarded-Proto $scheme` 头告知后端协议，后端 CORS 中间件能正确处理 HTTPS origin，无需额外改动。

### 18. Apple 开发者证书签名与公证

当前 `tauri.conf.json` 的 `bundle.macOS.signingIdentity` 为 `null`，构建出的 .app **未签名**。未签名的 macOS 应用在用户机器上会触发 Gatekeeper 拦截，需要右键打开或手动去隔离标记（见步骤 8.6.2），体验很差。正式分发前建议完成签名和公证。

#### 18.1 前置准备

1. 注册 [Apple Developer Program](https://developer.apple.com/programs/)（$99/年）
2. 在 Apple Developer 后台创建 **Developer ID Application** 证书（用于分发到 Mac App Store 以外的渠道）
3. 在钥匙串中导入证书，确认可用：

```bash
# 查看已安装的签名证书
security find-identity -v -p macappstore
# 示例输出：
#  1) 1234567890ABCDEF... "Developer ID Application: Your Name (TEAMID)"
```

#### 18.2 配置 tauri.conf.json 签名

```json
"bundle": {
  "active": true,
  "targets": ["app"],
  "icon": ["icons/icon.png"],
  "macOS": {
    "signingIdentity": "Developer ID Application: Your Name (TEAMID)",
    "entitlements": "Entitlements.plist"
  }
}
```

> `signingIdentity` 的值必须与 `security find-identity` 输出的证书全名**完全一致**。

#### 18.3 公证（Notarization）

签名后的 .dmg 还需要提交给 Apple 公证，否则首次打开时仍会提示"无法验证开发者"。

在 `tauri.conf.json` 的 `bundle.macOS` 中补充公证配置：

```json
"bundle": {
  "macOS": {
    "signingIdentity": "Developer ID Application: Your Name (TEAMID)",
    "entitlements": "Entitlements.plist",
    "providerShortName": "TEAMID"
  }
}
```

设置 Apple ID 凭据（通过环境变量或钥匙串，不要硬编码在配置文件中）：

```bash
export APPLE_ID="your@email.com"
export APPLE_ID_PASSWORD="xxxx-xxxx-xxxx-xxxx"    # App-Specific Password
export APPLE_TEAM_ID="TEAMID"
```

构建时 Tauri 会自动完成签名 + 公证：

```bash
bash up_build.sh
```

> 如果没有 Apple Developer 账号，可暂时跳过签名公证，让用户通过右键打开绕过 Gatekeeper（步骤 8.6.2），但正式分发强烈建议完成。
