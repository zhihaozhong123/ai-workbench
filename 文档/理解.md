#### 1. 什么是 多副本 backend 服务？Redis锁/信号量/缓存什么意思？为什么不能用chroma本地模式，要用chroma server 模式？

| 维度 | 多个 Backend 副本 | Redis 锁/信号量/缓存 | Chroma 本地模式 (PersistentClient) | Chroma Server 模式 |
|------|-------------------|---------------------|-----------------------------------|-------------------|
| **技术概念** | 多个服务实例，不同端口号 | Redis 提供的三种协调机制 | 嵌入式数据库，直接读写本地文件 | 独立的服务端，统一管理请求 |
| **生活比喻** | 🏪 **多个收银台** <br>同一家超市开了 2 个收银窗口 | 🔐 **排队系统** <br>• 锁 = 厕所单间（一次1人）<br>• 信号量 = 公共澡堂（一次N人）<br>• 缓存 = 快捷菜单（常用菜直接记） | 📒 **共用纸质账本** <br>所有收银员共用一本实体账本 | 💻 **电子收银系统** <br>所有收银员通过电脑下单，后台统一处理 |
| **工作原理** | • 2 个容器 = 2 个进程<br>• 端口 8000、8001<br>• 负载均衡分发请求 | • 锁：`SETNX` 命令，一次一个<br>• 信号量：`INCR` + 计数控制<br>• 缓存：`SET/GET` + `EXPIRE` | • 直接读写 postgreSQL + HNSW .bin 文件<br>• 没有跨进程锁保护<br>• 依赖文件系统锁（不可靠） | • Backend 通过 HTTP/gRPC 请求 Server<br>• Server 内部排队处理<br>• 统一管理文件读写 |

#### 3. 什么是 tenant 隔离？

> chroma server的tenant隔离，在项目里就是每个注册登录的用户的工作空间是独立的，tenant隔离是租户隔离的意思，但是不能理解为用户隔离，在这个项目可以理解为是用户的工作空间的隔离。租户隔离，类似于数据库隔离，每个数据库是独立的工作空间，每个数据库都有自己的不同的表。也可以把chroma server比喻成一个整栋美食广场大楼，tenant是每个独立的档口，每个档口都有自己的database，也就是卖的产品种类，collection相当于具体的菜品。

#### 7. 什么是多实例架构？

> 多实例架构指的是运行多个应用程序实例，每个实例都可以独立运行和扩展。在分布式系统中，多实例架构可以提高系统的可用性和可扩展性，通过负载均衡将请求分发到不同的实例上处理。

#### 8. 为什么要使用chroma server 模式？而不用chroma 本地模式？

> 使用chroma server 模式可以实现多实例横向扩展，通过负载均衡分发请求，提高系统的可用性和可扩展性。而chroma 本地模式是嵌入式数据库，没有跨进程锁保护，依赖文件系统锁（不可靠），无法满足多实例环境的需求。

#### 9. 什么是chroma server 模式？

> chroma server 模式是独立的服务端，统一管理请求，可以实现多实例横向扩展，通过负载均衡分发请求，提高系统的可用性和可扩展性。

#### 10. chroma 零知识设计具体怎么实现的？

> 写入 Chroma 只持久化 embedding + metadata，检索时再凭这些元数据回到用户自己的目录取片段。

> 原文的实际位置是用户在 user_kb_config 注册的 doc_dir（BYOC 自带存储）：后端只读、不复制、不落盘，PDF/Word 解析只在查询瞬间发生在内存。所以即使运营方能连上 Chroma，拿到的也只有向量 + 偏移 metadata，没有用户目录权限就还原不出文字。

#### 12. rerank 精排是什么？为什么默认关闭、且用百炼 API 而不是本地模型？

> **问题背景**：原检索是「BM25（关键词召回）+ 向量（语义召回）」两路混合，再用 RRF 把两套排名合并。
> RRF 只是按排名倒数求和的**启发式粗排**，它并不知道「用户问题」和「某块」到底有多相关，
> 所以融合后 top 块未必是真正最相关的——这正是 rerank 要补的精度环节。

> **为什么不在「余弦 + rerank」里删掉 BM25**：BM25 是召回的「安全网」，专治向量语义匹配不上、
> 但字面命中（人名/专有名词）的查询。rerank 只做排序、不做召回，两者职责不同、互补不可替换。

> **为什么选百炼 text-rerank API（而非本地 cross-encoder）**：
> - 本项目 embedding 建索引时明文**已经**走百炼 API 出网，rerank 查询时再发一次只是走同一信任边界，
>   并没有新增数据出网面（「零知识」在本项目指 Chroma 不落明文，与「不用第三方」不是一回事）；
> - 部署是 `1G/CPU × 2 副本、无 GPU`，本地 cross-encoder（如 bge-reranker-v2-m3 ≈ 2GB）放不进容器，
>   CPU 重排还会给每查询加 1~5 秒延迟，与当前部署直接冲突；
> - 百炼 rerank 中文效果好，且复用现有 OpenAI 兼容调用模式，无需下载大模型、不撑大镜像。
>   默认模型 `qwen3-rerank`（旧 `gte-rerank` 已于 2026-05-30 下线）；rerank 端点为
>   `{host}/compatible-api/v1/reranks`（与 embedding 的 `/compatible-mode/v1` 不同，旧 `/rerank` 路径已 404）。

> **可插拔 + 灰度**：rerank 抽象成可插拔 provider（默认 `bailian`，预留 `local` cross-encoder 接入点）。
> 若将来有「文本完全不出网」的硬隐私需求，给部署加内存/GPU 或独立 rerank 微服务后，把 `rerank_provider`
> 切到 `local` 即可，业务代码不动。`rerank_enabled` 默认 **false**（灰度），由 `user_kb_config` 逐库开启，
> 先观察延迟/成本/质量再全量；任何失败（限流/网络/provider 不可用）都会**回退 RRF 顺序**，绝不阻断检索。
> 
> **全局主开关（.env）**：`RERANK_ENABLED`（true/false）是 rerank 的**总闸**，在 `.env` 改一行、重启服务即全量切换，
> 无需逐个库调 API——最适合「随时整体开/关」与应急回退（`false` 覆盖所有逐库设置，等于一键 kill switch）。
> 逐库的 `rerank_top_k` / `rerank_provider` 仍保留作微调（DB 有值则覆盖全局默认）。另可在 `.env` 配
> `RERANK_TOP_K` / `RERANK_PROVIDER` / `ALIYUN_RERANK_MODEL` 调整全局默认值。
