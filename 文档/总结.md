# 总结：做 RAG Agent 与成熟后端项目的「思维轮廓」

> 对象：Agent 开发小白 + 初级 Web 后端 API 开发者。
> 目标：① 搞清楚「实现一个 RAG Agent 要想哪些事」；② 在脑袋里建立「一个可上线后端项目必须考虑的清单」。
> 约定：专有术语**首现时加粗**，并在「📖 术语卡」里给大白话解释。文档里引用了本项目（`xiaoshutong`）的真实做法作为例子，便于你对应理解。

---

# 第一大点：实现一个 RAG Agent 要想哪些事（一问一答）

> RAG = **R**etrieval-**A**ugmented **G**eneration（检索增强生成）。先去知识库里「找」相关片段，再让大模型「基于片段答」，而不是让模型凭空编。

---

### Q1：为什么需要 RAG？大模型自己不会答吗？

**答**：大模型有两个硬伤——① **知识有截止日期**（训练完就不变了）；② **不知道你的私有文档**（公司手册、个人笔记它没见过）。
RAG 就是给模型外挂一个「私人资料库」：用户提问 → 先检索相关资料 → 把资料塞进提示词 → 模型基于资料作答。这样既能用上私有数据，又能大幅减少「胡说八道（幻觉）」。

📖 术语卡：**幻觉（Hallucination）** = 模型一本正经地编出不存在的内容。RAG 通过「强制模型依据检索到的原文回答」来压制幻觉。

---

### Q2：知识库里一堆文档，怎么喂给模型？

**答**：不能直接整本丢进去（会超出模型上下文长度，且重点被淹没）。要先**切分（Chunking）**：

- 把文档切成固定大小的「块」（chunk），例如 `chunk_size=512` 字，块与块之间留 `overlap=64` 字重叠，避免一句话被切断。
- 更高级的做法是**语义切分**：按意思自然断句，而不是死按字数切。
- 切多大、重叠多少，不是拍脑袋，而是用「评估脚本」在数据上测出来的（见 Q12）。

📖 术语卡：**上下文窗口（Context Window）** = 模型一次能「看到」的最大 token 数。超出就截掉，所以必须先把文档切小、只挑相关的喂进去。

---

### Q3：「检索」到底怎么找到相关块？embedding 是什么？

**答**：靠**向量检索**。

1. **Embedding（嵌入）**：用一个模型把每段文本变成一串数字（向量）。语义相近的文本，向量在空间里距离就近。
2. 建库时：每小块文本 → 算 embedding → 存进向量数据库（本项目用 Chroma）。
3. 提问时：把问题也算成 embedding → 在库里找「距离最近」的若干块 → 返回。

📖 术语卡：**向量数据库** = 专门存「文本向量」并支持「按相似度快速找最近邻居」的数据库（如 Chroma、Milvus、pgvector）。**相似度阈值** = 一个分数下限，低于它的块被认为「不相关」被丢弃。

---

### Q4：top_k 和相似度阈值，分别管什么？

**答**：两者配合才是完整召回逻辑：

- `top_k` = **召回上限**：先把最相似的 k 个块捞回来（例如 8 个）。
- `similarity_threshold` = **召回下限**：在这 k 个里，再砍掉分数低于阈值的（例如 0.1）。
- 先按 top_k 取候选，再用阈值过滤，最后还可能被 `max_return_chunks` 截断——才是真正喂给模型的块。

> 本项目做法：阈值定得低一点（0.1），因为 BM25 关键词命中的块（见 Q5）永远保留，阈值只当向量召回的「下限兜底」，避免把含关键事实但向量分不高的块误杀。

---

### Q5：纯向量检索够吗？为什么还要 BM25？

**答**：不够。**向量检索擅长「语义相似」，但不擅长「字面精确匹配」**。
例子：问「主人公叫什么名字」，文档里写的是「我叫钟俊皓」。向量检索可能把这句排到 top_k 之外；但「钟俊皓」这三个字是**字面**命中，用传统关键词算法 BM25 就能精准捞到。

本项目用**混合检索**：向量召回 + BM25 召回，再用 **RRF（Reciprocal Rank Fusion，倒数排名融合）** 把两边结果合并排序。专治「按名字/专有名词找片段」这类向量短板。

📖 术语卡：**BM25** = 老牌关键词相关性算法（搜索引擎同款），按词频/逆文档频率打分，不做语义理解，但字面命中极准。**RRF** = 把多个召回列表按「排名倒数」加权融合，不依赖各算法分数绝对值是否可比。

---

### Q6：多个用户的数据，怎么保证互不串门？

**答**：**多租户隔离（Multi-tenancy）**。每个用户的知识库完全独立：

- 本项目用 Chroma 原生的 `tenant / database` 隔离——每个用户在 Chroma 里有独立命名空间，应用层就算有 bug，数据库层也挡死跨用户读取。
- 检索路由只认 **JWT 里的 user_id**（见第二大点认证），绝不接收外部指定的库名。
- 短期对话历史用 `thread_id = 用户:会话:段` 天然隔离。
- **长期记忆同样下沉到了存储层隔离（双保险）**：热存储（Chroma）按用户 `tenant=<user_id>` / `database=mem_<user_id>` 隔离；冷存储（PostgreSQL）按用户独立 schema `mem_<user_id>.cold_memories` 隔离。即使应用层漏写 `WHERE thread_id`，直接连底层存储也只能命中本用户的数据。详见 Q9 与「第二大点·第 3 点」。

📖 术语卡：**租户（Tenant）** = 一个独立用户/客户。多租户 = 一套系统服务多个用户，但彼此数据隔离，像「一栋楼里每户一把独立锁」。

---

### Q7：用户文档很隐私，运营方能不能看到原文？

**答**：可以设计成**「零知识」**——运营方只存向量和定位信息，不存原文。

本项目做法：`store_text=False`，Chroma 里**只存向量 + 元数据（文件名、字符偏移）**，不持久化任何原文文本。检索时，再凭元数据从**用户自己的目录**按偏移实时取回片段。运营方没有用户目录的权限 → 取不到原文，也看不到向量对应的文字。PDF/Word 同理，解析只在查询瞬间发生在内存、不落盘。

---

### Q8：Agent 是怎么「会调用工具」的？ReAct 是什么？

**答**：本项目用 **ReAct（Reason + Act）** 架构：模型不是一次性输出答案，而是循环「思考 → 调工具 → 看结果 → 再思考」。

- **思考**：模型决定「我需要查知识库」；
- **行动**：调用 `search_knowledge_base` 工具；
- **观察**：拿到工具返回的片段；
- 重复，直到模型认为能答了，才输出最终回复。

工具清单（本项目）：知识库检索、联网搜索、计算器、获取时间、长期记忆存取、发邮件、打开本机应用等。

📖 术语卡：**ReAct** = 把「推理（Reason）」和「行动（Act）」交织起来的 Agent 范式，让模型能边查边想，而不是盲答。**Tool Calling（工具调用）** = 模型输出「我要调 XX 函数，参数是 YY」，由框架真正执行函数并把结果喂回模型。

---

### Q9：记忆怎么设计？对话太长会爆吗？

**答**：分两层：

- **短期记忆** = 当前这轮对话的历史。本项目由业务 `messages` 表存储，每轮上下文从表读取后回传给 Agent，天然按会话/用户隔离，不使用 LangGraph checkpointer。长会话建议在业务层对回传历史做截断/摘要，避免上下文无限膨胀。
- **长期记忆** = 关于「用户是谁」的画像/事实（如偏好、关键信息），跨会话保留。本项目存向量库，聊天时动态检索「已知用户画像」注入提示词，做到「越聊越懂你」。

> **长期记忆的隔离设计（双保险）**：长期记忆也走「应用层过滤 + 存储层隔离」两层。
> - 应用层：每条记忆都打 `thread_id`（= `user_id`）标签，检索时按 `thread_id` 过滤。
> - 存储层：① 热记忆存 Chroma 时，按用户 `tenant=<user_id>` / `database=mem_<user_id>` 各自独立的集合，即使应用层过滤出 bug，直接连 Chroma 也看不到他人数据；② 冷记忆存 PostgreSQL 时，每个用户独立 schema `mem_<user_id>.cold_memories`（`user_id` 规范化为合法标识符，前缀 `mem_` 防冲突），即使 SQL 漏写 `WHERE thread_id` 也只命中本用户。
> - 迁移：系统从「旧版共享集合/共享表」升级时，启动会自动把存量记忆按 `user_id` 迁移到各租户（幂等：Chroma 用 `upsert`、PG 逐用户迁完才删旧行；旧 Chroma 集合删除、旧表改名 `cold_memories_legacy_bak` 备份），重复启动不重复迁移、不产生重复数据。

---

### Q10：模型会不会陷入死循环或卡死？

**答**：会的，所以要加护栏：

- `recursion_limit`：限制一轮对话里「思考→调工具」的最大层数（本项目 12 层），防无限递归。
- **循环检测**：连续重复调同一个工具超过 N 次（本项目 3 次）就主动中断。
- **整体超时**：单轮对话设超时（本项目 `chat_timeout_seconds`），到点强制中断返回兜底提示，防止一个卡死的模型/工具把连接一直占着拖垮整个服务。

---

### Q11：模型会不会「没做的事说做了」？

**答**：会，这叫**谎报**。本项目专门做了「诚实护栏」：

- 若回复说「邮件已发送」，但本轮**没有**发信工具的成功回执 → 纠正为「我刚才并没有真正发出去」，杜绝谎报。
- 同理适用于「已打开应用/网页」等真实操作类工具。

核心思路：模型的「文字声明」不可信，**以工具的真实回执为权威**，不符就纠正。

---

### Q12：切分/召回参数怎么定？靠猜吗？

**答**：不靠猜，靠**评估（Evaluation）**，且已**全自动、按库隔离**。本项目通过在线校准 `kb_calibration` 完成：

1. 用户在前端对「自己的某份知识库」点「校准」；
2. 后台按该库的 `doc_dir`（用户真实上传目录，BYOC 只读不复制）现生成标注集（仅内存、不落盘保护隐私），用当下物理文件建内存索引；
3. 扫描 `top_k` / `similarity_threshold` 网格，挑 recall 高、噪声低的最优组合；
4. 自动写回该库 `user_kb_config` 并热替换重建索引——无需人工改任何文件。

底层标注/判卷逻辑在 `scripts/build_golden.py`（`build_golden_for_dir`）与 `scripts/_eval_common.py`（`recommend_topk_threshold` / `build_index` / `node_relevant`），它们是校准的内部库，不再有独立离线 CLI（原 `eval_chunking.py` / `eval_topk.py` / `eval_threshold.py` / `run_eval.py` 已移除）。

📖 术语卡：**Recall@k（召回率）** = 标准答案里「相关块被找回来」的比例。越高越好。**噪声率** = 找回来的块里「不相关」的比例。越低越好。调参目标：在高 recall 和低噪声之间取平衡。

---

### Q13：建索引很贵（embedding 要钱/要额度），怎么省？

**答**：两个手段：

- **增量复用**：给每块文本算指纹 `text_hash`（含 embedding 模型标识）。文档没改的块，直接复用旧向量，只对新块算 embedding，省额度。
- **重试 + 指数退避**：embedding 服务有 QPS 限额，遇 429 限流就重试，等的时间逐次翻倍（如 1s→2s→4s），扛住抖动不中断整库构建。

> 注意：embedding 模型升级后，旧向量语义空间变了，**必须全量重建**（指纹里编了模型标识，自动检测）。

---

### Q14：前端「逐字输出」是怎么实现的？

**答**：用**流式（Streaming）**。模型不是等全部生成完才返回，而是边生成边把 token（字）推给前端，形成打字机效果。本项目用 SSE/WebSocket + `astream`，并做了细节处理：只推「最终回复」的 token，工具调用阶段的中间思考文字不推（或先清掉），避免用户看到混乱内容。

📖 术语卡：**SSE（Server-Sent Events）** = 服务器向浏览器单向持续推送文本的轻量协议，适合逐字输出。**WebSocket** = 全双工长连接，前后端可互相发消息，适合聊天。

---

### 小结：RAG Agent 的「检查清单」

| 维度 | 要想的事 |
|------|----------|
| 数据 | 文档怎么切（chunking）？支持哪些格式（pdf/docx）？ |
| 召回 | embedding 模型选谁？top_k/阈值怎么定？要不要混合检索（BM25+RRF）？ |
| 隔离 | 多租户怎么隔开？隐私要不要「零知识」？ |
| Agent | 用 ReAct 还是别的？有哪些工具？循环/超时/谎报怎么防？ |
| 记忆 | 短期怎么存/压缩？长期画像怎么累积？ |
| 成本 | embedding 额度怎么省（增量复用）？限流怎么扛（重试退避）？ |
| 质量 | 怎么评估（golden + recall/noise）？参数怎么校准？ |
| 体验 | 流式输出？来源标注？ |

# 第二大点：成熟可上线后端项目的「思维轮廓」

> 目标：脑袋里建立一张**清单**。以后做任何后端项目，挨个过一遍，缺哪个补哪个。下面每一条都配「本项目怎么做」作例子。

---

## 0. 先把「非功能需求」刻进脑子

功能能跑 ≠ 能上线。**能上线的标准是**：安全、不崩、不串数据、出问题能查、挂了能恢复、人多了能扛。下面所有点都属于「非功能需求」，是高级后端的分水岭。

---

## 1. 配置管理（Configuration）

**要考虑**：所有环境相关的值（数据库地址、密钥、超时、开关）**绝不能写死在代码里**，要走配置文件 / 环境变量。并用类型校验（本项目用 Pydantic `Settings`）保证格式正确。

**本项目例子**：
- `.env` + Pydantic `Settings` 加载，`extra="ignore"` 容错。
- **生产环境启动校验**：`env=production` 时强制 `JWT_SECRET` 不能是默认值，否则直接拒绝启动——防弱密钥上线。

📖 术语卡：**环境变量（Env Var）** = 操作系统层面注入的键值对（如 `DB_HOST=localhost`），不进代码仓库，避免泄露密码。**Pydantic** = Python 的数据校验库，自动把配置转成带类型的对象并校验。

---

## 2. 认证与授权（AuthN / AuthZ）

**要考虑**：
- **认证（AuthN）**：你是谁？→ 用 **JWT（JSON Web Token）**。
- **授权（AuthZ）**：你能干啥？→ 基于用户身份/角色限制操作。
- **双 Token 机制**：短期 `access_token`（如 15 分钟，被盗损失小）+ 长期 `refresh_token`（如数天，用来换新的 access）。

**本项目例子**：`config.py` 里有 `jwt_secret / jwt_algorithm / access_token_expire_minutes / refresh_token_expire_hours`；生产禁用弱密钥。

📖 术语卡：**JWT** = 一串签名令牌，服务端用密钥签名，客户端后续请求带着它，服务端验签名即可信其身份，无需每次查库。**认证 vs 授权**：认证="证明你是你"；授权="确认你被允许做这事"。

---

## 3. 多租户隔离（Multi-tenancy）

**要考虑**：只要是「多用户系统」，就必须从**数据库层、检索层、会话层**三处保证数据互不串门。隔离最好下沉到存储引擎（如本项目的 Chroma tenant/database），即使应用层出 bug 也隔得开。

**本项目例子**：Chroma 原生 tenant/database 隔离；检索路由只认 JWT 的 `user_id`；对话 `thread_id` 含用户标识。**长期记忆同样下沉到存储层**——Chroma 按 `tenant=<user_id>` / `database=mem_<user_id>` 隔离热记忆，PostgreSQL 按每用户独立 schema `mem_<user_id>` 隔离冷记忆，形成「应用过滤 + 存储隔离」双保险（详见第一类 Q6/Q9）。

---

## 4. 限流与配额（Rate Limiting & Quota）

**要考虑**两件事，别混：
- **限流（防刷/防爆破）**：按「客户端 IP」或「用户」限制单位时间请求数。登录/注册接口要**更严**（防密码爆破、防刷 JWT）。
- **配额（防膨胀）**：限制单用户能占的资源（知识库数量、文档数、总大小），避免一个大户拖垮其他人。

**本项目例子**：
- `ratelimit.py`：按 IP 双桶（普通 `rate_limit_per_minute` / 鉴权 `rate_limit_auth_per_minute`），超了返回 **HTTP 429**。
- `config.py`：`kb_max_per_tenant / kb_max_docs_per_kb / kb_max_doc_bytes` 等资源配额。

📖 术语卡：**HTTP 429** = "Too Many Requests"，表示被限流。**固定窗口限流** = 每 60 秒一个窗口，窗口内计数超阈值就拒，本项目用 Redis 的 `INCR+EXPIRE` 实现，多实例共享计数。

---

## 5. 并发与多实例（Concurrency）

**要考虑**：现代后端是**异步 + 多副本**的：
- **异步（asyncio）**：I/O 密集型（等数据库、等模型）用异步，单进程扛高并发。
- **多实例**：起多个副本做负载均衡，所以**所有共享状态必须外置**（锁、信号量、计数、缓存都放 Redis），不能只存在单机内存。
- **隔离上下文**：多用户并发时，用 `thread_id` / `user_id` 等把请求上下文隔开，并善用「上下文变量（contextvar）」在异步调用链里传递身份，避免串号。

**本项目例子**：
- 全程 `async`（FastAPI + LangGraph 异步）。
- `config.py` 注释明确：锁/信号量/队列/限流全部走 **Redis**，"支持多实例水平扩展"。
- 建索引并发受 `kb_build_concurrency` 信号量控制，避免打爆 embedding 配额。

---

## 6. 超时、重试、退避（Timeout / Retry / Backoff）

**要考虑**三件套，缺一会雪崩：
- **超时**：任何外部调用（LLM、数据库、文件读取）都要设超时，否则一个卡死占满连接 → 全站挂。
- **重试**：网络抖动偶发失败，重试几次。
- **指数退避**：重试间隔逐次翻倍（1s→2s→4s），避免重试本身把对方打爆（尤其对方在限流时）。

**本项目例子**：
- `llm_request_timeout`（单请求）、`chat_timeout_seconds`（整轮）、`kb_read_timeout`（读用户文件）多层超时。
- `rag_tool.py` 的 `_embed_with_retry`：遇 429 重试 + `embed_retry_base ** attempt` 指数退避。
- LLM 调用 `max_retries=3`。

---

## 7. 错误处理与优雅降级（Resilience）

**要考虑**：外部依赖（模型、向量库、用户网盘）随时可能挂。**别让一个依赖挂了把主流程带崩**：
- **降级**：BM25 建索引失败 → 退化为纯向量检索；用户网盘不可达 → 诚实返回「取不到原文」而非崩溃。
- **best-effort（尽力而为）**：重置数据的脚本即使 PG 暂不可达也只告警、不抛异常阻断启动。
- **兜底回复**：聊天整体超时 → 返回「请稍后再试」，而不是 500 错误。

---

## 8. 数据安全与隐私（Security & Privacy）

**要考虑**（ Checklist）：
- 密钥/密码不进代码、不进日志。
- 密码存储用**哈希**（加盐），绝不明文。
- 传输用 HTTPS；CORS 只允许可信前端来源。
- 用户输入必须**校验**（Pydantic Schema），防注入。
- 隐私数据尽量「零知识」存储（见 Q7）。
- 工具/高危操作要有权限判断（如发邮件前确认凭证就绪）。

📖 术语卡：**CORS（跨域资源共享）** = 浏览器安全机制，限制"A 网站的前端"能否调"B 网站的后端"。后端要显式放行可信来源。**哈希** = 把密码变成不可逆的摘要，验证时比摘要而非比明文，数据库泄露也拿不到原密码。

---

## 9. 审计日志（Audit Log）

**要考虑**：所有**敏感操作**（登录、注册、删知识库、发邮件、对话）要留不可篡改的痕迹，便于事后追责与风控。审计日志通常用**独立 logger + 结构化 JSON**，不落业务表（避免表膨胀），交给日志系统（ELK/Loki）集中收集。

**本项目例子**：`audit.py` 的 `log_audit(user_id, action, target, detail, ip)`，覆盖 login/register/kb_delete/chat 等。

---

## 10. 可观测性（Observability）：日志 / 指标 / 链路

**要考虑**三支柱：
- **日志（Logging）**：分 `text`（本地调试）和 `json`（生产，方便机器采集）两格式。
- **指标（Metrics）**：关键数字暴露出来（请求量、延迟、成功率、失败次数），接 Prometheus / Grafana 看板告警。
- **健康检查（Health Check）**：`/healthz` 端点，让负载均衡/容器编排知道「我还活着」。

**本项目例子**：
- `config.py` 的 `log_format = json/text`。
- `metrics.py`：用 prometheus_client 暴露建索引成功率、检索延迟直方图、embedding 失败数；`/metrics` 供拉取。
- `main.py` 提供 `/healthz`、`/metrics`、`/metrics.json`。

📖 术语卡：**Prometheus** = 时序指标数据库，定时来拉 `/metrics` 数据；**Grafana** = 把指标画成图表的看板。**直方图（Histogram）** = 把延迟分成多个区间计数，能算出 P95/P99 等分位数（"99% 的请求在 X 秒内完成"）。

---

## 11. 备份与灾备（Backup & DR）

**要考虑**：数据库和向量库都要**自动备份 + 保留策略**。生产环境「没备份 = 裸奔」。

**本项目例子**：`docker-compose.yml` 里两个备份服务——`pg-backup`（PostgreSQL 每日 `pg_dump`，保留 7 天）、`chroma-backup`（Chroma 每 6h 快照，保留 7 天）。

---

## 12. 部署与生命周期（Deployment）

**要考虑**：
- **容器化**：Dockerfile + docker-compose，环境一致、一键起停。
- **只读根 + 最小暴露**：后端只监听 `127.0.0.1`（本机），对外经反代（Nginx/Caddy）暴露；生产关闭 `/docs` 调试文档。
- **平滑启停**：启动做初始化（连库、建表、加载模型），关闭释放资源。本项目用 FastAPI 的 `lifespan` 管理。
- **水平扩展**：无状态化 + Redis 共享，副本数随流量增减。

---

## 你脑袋里的「成熟后端轮廓」一句话版

> **配置外置且生产校验 → 认证授权双 Token → 多租户三层隔离 → 限流防刷 + 配额防膨胀 → 异步+Redis 支撑多实例并发 → 超时/重试/退避三件套防雪崩 → 优雅降级不连环崩 → 隐私零知识+输入校验 → 审计留痕 → 日志/指标/健康检查三可观测 → 自动备份 → 容器化最小暴露。**

把这 12 条当成"上线前 checklist"，逐条打勾，就是**高级后端的思维方式**。
